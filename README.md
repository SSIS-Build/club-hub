# SSIS BUILD

**Have an idea. Make it real.**

SSIS BUILD is the home of the **HS Coding & Digital Making Club at SSIS**.

We build useful, creative, experimental and occasionally ridiculous things with code and technology.

You do **not** need to be an expert programmer.  
You do need to be curious, willing to experiment, and ready to make things.

---

## What can we build?

Pretty much anything involving code, technology or digital making.

Examples:

- Websites
- Apps
- Games
- AI tools
- Automations
- Mathematical applets
- Simulations
- Data visualisations
- Interactive art
- School tools
- APIs and bots
- Raspberry Pi projects
- Arduino projects
- Hardware builds
- Something nobody has thought of yet

---

## How SSIS BUILD works

Our basic workflow is:

**IDEA → PROTOTYPE → BUILD → TEST → SHARE → IMPROVE**

### 1. Find an idea

Start with:

- a problem you want to solve
- something you wish existed
- something you want to learn
- something useful for SSIS
- something interesting
- something fun

### 2. Start small

Ask:

> **What is the smallest version of this idea that could actually work?**

Build that first.

### 3. Create a project

Once an idea becomes a real project, it gets its own GitHub repository.

### 4. Build

Use whatever tools make sense.

### 5. Test

Try to break it.

Ask other people to try it.

### 6. Share

Show unfinished work as well as finished work.

### 7. Improve

Use feedback to make the project better.

---

## Club principles

### Build things

We learn by making.

### Start small

A tiny working project is better than a huge unfinished one.

### Experiment

It is completely fine for an idea not to work.

### Share what you learn

If you discover something useful, help somebody else.

### Ask for help

Being stuck is part of building.

### Use AI intelligently

AI tools are welcome.

Use them to:

- brainstorm
- generate starter code
- explain unfamiliar code
- debug
- refactor
- create tests
- explore new technologies
- improve documentation

But:

> **Your team owns what it publishes.**

You should be able to explain what your project does, test whether it works, and take responsibility for the result.

### Make things people can try

Whenever possible, turn projects into something that someone else can actually use.

| 🔵 **Prototype** | First working experiment |
| 🟡 **Building** | Active development |

| 🏆 **Showcase** | Ready to share |

# Starting a new project

When your group is ready:

1. Agree on the basic idea.
2. Decide on the **smallest working version**.
3. Give the project a short, clear name.
4. Create a GitHub repository.
5. Add a README.
6. Build the first prototype.
7. Commit your progress regularly.
8. Share it with the club.

---

## Every project README should explain

- **What is this?**
- **Why are we building it?**
- **Who is it for?**
- **How can someone try it?**
- **What technology does it use?**
- **Who is working on it?**
- **What works now?**
- **What might we add next?**

# Getting help

If something is not working, don't just write:

> "It doesn't work."

Try to explain:

### What are you trying to do?

### What should happen?

### What actually happens?

### What have you already tried?

### What error message do you get?

### Can you share the GitHub repository?

Good questions make debugging much easier.

---

# Safety and privacy

Never commit:

- passwords
- API keys
- access tokens
- private student information
- confidential school information
- personal data belonging to other people

Use `.env` files and `.gitignore` where appropriate.

If you are unsure whether something should be public, **ask before publishing it**.
